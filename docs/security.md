## 2. Secret Management

### 2.1 Hierarchy

| Environment | Storage |
|---|---|
| Local dev | `.env` file (gitignored) — generated by `init_project.py` |
| CI/CD | GitHub Secrets / GitLab CI Variables / Azure DevOps Library |
| Staging/Production | Azure Key Vault / AWS Secrets Manager / Doppler / Vault |

### 2.2 Rules

- **ห้าม** `git push` `.env` หรือ `project.config` — มีใน `.gitignore` แล้ว:
  ```
  .env
  .env.*
  !.env.example
  project.config
  ```
- **ห้าม** ใส่ secret ใน Dockerfile (`ENV API_KEY=...`) — ใช้ runtime injection
- **ห้าม** echo secret ใน logs/CI output — mask via secret manager
- **Rotation:** secrets ต้องหมุนทุก:
  - 90 วันสำหรับ general API keys
  - 30 วันสำหรับ database credentials ใน production
  - ทันทีหลัง security incident
- **Pre-commit hook:** ติดตั้ง `detect-secrets` หรือ `gitleaks`

### 2.3 Generating Secrets

```bash
# JWT secret (32-byte hex)
openssl rand -hex 32

# Random password (24 chars)
openssl rand -base64 24 | tr -d "=+/" | cut -c1-24
```

`init_project.py` generate `JWT_SECRET_KEY` อัตโนมัติเมื่อ run ครั้งแรก

## 3. Input Validation

### 3.1 Pydantic-First

ทุก request body **ต้อง** ใช้ Pydantic schema — ห้ามรับ `dict` หรือ raw JSON ใน endpoint:

```python
# ❌ Wrong
@router.post("/items")
async def create_item(payload: dict): ...

# ✅ Right
@router.post("/items")
async def create_item(payload: ItemCreate): ...
```

### 3.2 String Length Limits

ทุก string field ต้องมี max_length:

```python
class Item(BaseModel):
    name: str = Field(min_length=1, max_length=200)
    description: str | None = Field(default=None, max_length=5000)
```

### 3.3 Patterns/Enums

```python
class Product(BaseModel):
    sku: str = Field(pattern=r"^[A-Z0-9-]{3,32}$")
    status: Literal["draft", "active", "discontinued"]
```

### 3.4 SQL Injection

SQLAlchemy 2.0 ป้องกัน SQL injection โดย default — **ห้าม** ใช้ string concatenation/f-string ใน SQL:

```python
# ❌ Wrong (SQL injection!)
await db.execute(text(f"SELECT * FROM users WHERE email = '{email}'"))

# ✅ Right
await db.execute(text("SELECT * FROM users WHERE email = :email"), {"email": email})

# ✅ Better (using ORM)
result = await db.execute(select(User).where(User.email == email))
```

### 3.5 File Uploads

```python
from fastapi import File, UploadFile, HTTPException

ALLOWED_MIME = {"image/jpeg", "image/png", "application/pdf"}
MAX_SIZE = 10 * 1024 * 1024  # 10 MB

@router.post("/upload")
async def upload(file: UploadFile = File(...)):
    if file.content_type not in ALLOWED_MIME:
        raise HTTPException(status_code=400, detail="Unsupported file type")

    size = 0
    while chunk := await file.read(1024 * 1024):
        size += len(chunk)
        if size > MAX_SIZE:
            raise HTTPException(status_code=413, detail="File too large")
```

**Hard rules for uploads:**
- ห้ามใช้ user-supplied filename ตรงๆ ใน path — generate UUID
- ห้าม store ใน static directory ที่ serve โดย web server
- Scan for malware ถ้ามี budget (ClamAV, cloud AV API)

### 3.6 SSRF — Server-Side Request Forgery

> **กฎ:** AGENTS.md §3 ข้อ 9 — ห้าม fetch user-provided URL ฝั่ง server เว้นแต่ผ่าน guard
>
> สถิติ: AI tools ที่ทดสอบ **สร้าง SSRF 100%** เมื่อต้อง build URL-fetching feature
> (Tenzai, Dec 2025) — เป็นช่องที่ "เสี่ยงสุด" จึงต้องมี tooling จับ ไม่ใช่แค่ความจำ AI

ทุก outbound fetch ที่ URL มาจาก request input (body/query/param) **ต้อง** ผ่าน
`assert_safe_url()` จาก `app/core/safe_url.py` ก่อนยิงออก:

```python
# ❌ Wrong — SSRF: attacker ชี้ url ไป http://169.254.169.254/ (cloud metadata)
@router.post("/preview")
async def preview(payload: PreviewRequest):
    async with httpx.AsyncClient() as client:
        resp = await client.get(payload.image_url)   # ← unguarded
    return resp.text

# ✅ Right — guard ก่อน fetch
from app.core.safe_url import assert_safe_url

@router.post("/preview")
async def preview(payload: PreviewRequest):
    safe = assert_safe_url(payload.image_url)        # raises UnsafeURLError
    async with httpx.AsyncClient() as client:
        resp = await client.get(safe)
    return resp.text
```

`assert_safe_url()` block:
- scheme ที่ไม่ใช่ `http`/`https` (เช่น `file:`, `ftp:`, `javascript:`)
- host ที่ resolve เป็น **private / loopback / link-local / reserved / multicast**
  — รวมถึง `169.254.169.254` (cloud metadata), `127.x`, `10.x`, `192.168.x`, `::1`
  และ IPv4-mapped IPv6 (`::ffff:169.254.169.254`)
- รองรับ `allowed_hosts={...}` เมื่อต้องการ allowlist เฉพาะ host ที่รู้จัก

**Enforcement:** `scripts/checks/no_unguarded_url_fetch.py` (pre-commit) flag เฉพาะ
fetch ที่ URL root มาจาก user input — outbound call ที่ใช้ `settings.*`/constant
(Azure SSO, JWKS, Graph, Registry telemetry) **ไม่โดน** เพราะไม่ใช่ user-controlled.
ถ้า URL ปลอดภัยจริงแต่ pattern หลบ static analysis ไม่ได้ → เติม `# ssrf-ok` บนบรรทัด

**ข้อจำกัด (รู้ไว้):** guard นี้ validate ตอนเรียก — DNS rebinding (TOCTOU) ยังเป็นไปได้
ในทางทฤษฎี สำหรับ path ที่ต้อง assurance สูง ให้ resolve ครั้งเดียวแล้ว connect ไป IP
ที่ validate แล้ว หรือใช้ `allowed_hosts` allowlist

#### 3.6.1 Database Connections module — host allowlist (L3 TODO)

Feature module `FEATURE_DB_CONNECTIONS` (opt-in — ดู [`patterns/db-connections.md`](patterns/db-connections.md))
เปิดให้ **super_admin** ลงทะเบียน external PostgreSQL `host:port` ผ่าน UI แล้วต่อ
ออกไป — เป็น SSRF surface โดยเนื้อแท้ (admin ชี้ไป internal host / cloud metadata
proxy ที่พูด postgres protocol ได้) แต่ `assert_safe_url()` ใช้ไม่ได้ตรงๆ เพราะ
นี่คือ DB connection ไม่ใช่ HTTP fetch และ "fetch internal host" คือ use case จริง.

ปัจจุบัน mitigation คือ **trust boundary**: คีย์ทั้งสามอยู่ใน `users.py`
`_PRIVILEGE_MANAGEMENT_KEYS` (super_admin เท่านั้น, per-user override ให้ไม่ได้) +
ทุก mutation/query ลง activity_logs (risk `high`).

> **L3 TODO (business-critical / external-facing):** เพิ่ม **host allowlist** สำหรับ
> connection targets — env เช่น `DB_CONNECTIONS_ALLOWED_HOSTS` (comma-separated
> host/CIDR) ที่ block private/loopback/link-local + `169.254.169.254` ยกเว้น host
> ที่ allow ชัดเจน, validate ใน `db_connection_service._build_url` ก่อนสร้าง engine.
> ติดตามใน roadmap ของโปรเจกต์ก่อนเปิด module นี้บน MATURITY_LEVEL=L3.

## 4. CORS

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.API_CORS_ORIGINS,  # explicit list, never ["*"]
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type", "X-Request-Id"],
    max_age=600,
)
```

**Rules:**
- Production `API_CORS_ORIGINS` ต้องเป็น explicit list ของ frontend URLs
- Dev อาจใช้ `["http://localhost:5173"]`
- ห้าม `["*"]` กับ `allow_credentials=True`

| Endpoint | Limit | Scaffold default |
|---|---|---|
| `/auth/login` | 5/minute per IP | ✅ enforced (v3.0.6 HIGH-1) |
| `/auth/sso/callback` | 3/minute per IP | ✅ enforced (v3.0.6 HIGH-1) |

Wiring: `app/core/rate_limit.py` exports a `limiter` singleton that

limits with `@limiter.limit("N/minute")` on the route function (the
function MUST accept `request: Request` — slowapi reads the client
address from there).

### 6.4 Production storage + proxy trust (Round-4 HIGH-2)

Per-worker counters are NOT real rate limits. The Round-4 HIGH-2 fix
adds two env knobs and a startup gate so production cannot silently
ship with broken limits.

| Env var | Purpose | Dev default | Production REQUIRED |
|---|---|---|---|
| `RATE_LIMIT_STORAGE_URI` | Where slowapi stores counters | `memory://` | `redis://host:6379/0` (or another shared backend) |
| `TRUSTED_PROXY_IPS` | Comma-separated CIDR list whose `X-Forwarded-For` we trust | empty (no proxy) | **every** proxy hop's CIDR — ask Infra, never guess |

**Fail-fast gate (round 8-16D):** `app/core/config.py` refuses to boot when
`APP_ENV == "production"` and any of these hold:

| Condition | Why it is fatal |
|---|---|
| `RATE_LIMIT_STORAGE_URI` starts with `memory:` | per-worker counters — `--workers 4` makes every limit 4× looser, × N replicas |
| `TRUSTED_PROXY_IPS` empty | behind nginx, every request is attributed to nginx's own IP → all clients share ONE bucket |
| `TRUSTED_PROXY_IPS` has an entry that isn't a valid IP/CIDR | `_parse_proxy_networks` drops bad entries with only a stderr warning; an unsubstituted `.env.prod.example` placeholder would silently yield zero trusted proxies |
| `API_CORS_ORIGINS` contains `localhost`/`127.0.0.1` | the dev default leaked to production |
| `APP_DEBUG` is true | tracebacks returned to clients |

The first raises pydantic's `ValidationError`; the rest raise
`ProductionConfigError` (a `RuntimeError`). That distinction is deliberate:
pydantic wraps a `ValueError` from a validator into a `ValidationError`
whose message echoes the raw settings input — i.e. every env-sourced secret
— so the new checks raise a non-`ValueError` that propagates untouched. See
the class docstring in `app/core/config.py`.

**Proxy IP trust.** When `TRUSTED_PROXY_IPS` is empty, `request.client.host`
is used verbatim — safe only for direct exposure. When set, the resolver in
`app/core/rate_limit._client_ip` walks `X-Forwarded-For` **from the right**,
returning the first hop that is NOT itself a trusted proxy (RFC 7239 §5.2).

> Walking rightward is the whole point. nginx's
> `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` **appends**
> rather than replaces, so a client-supplied value ends up **leftmost** —
> taking the leftmost entry would hand any attacker a fresh bucket per
> request. (Earlier revisions of this document described leftmost behaviour;
> that was never what the code did.)

**List every hop, not just the nearest one.** The deployed chain is
`client → IT proxy → frontend nginx → backend`, so the backend sees peer =
nginx container and `X-Forwarded-For: <real-client>, <IT-proxy-ip>`. If the
IT proxy's own IP is omitted from `TRUSTED_PROXY_IPS`, the walk stops there
and reports the **proxy** as the client — every user shares one bucket while
the limiter still looks healthy. Conversely, do **not** trust the whole
Docker bridge subnet: `proxy-net` is shared with other applications, and any
container on it could then spoof `X-Forwarded-For`.

**Redis IS a hard dependency when `RATE_LIMIT_STORAGE_URI` is `redis://`.**
`limits` (transitive via slowapi) has **no** built-in Redis client:
`storage_from_string("redis://…")` raises
`ConfigurationError: 'redis' prerequisite not available`. slowapi builds its
`Limiter` at import time, so a production container pointed at Redis without
the client installed **never boots**. `backend/pyproject.toml` therefore
declares `limits[redis]>=5.8.0` (round 8-16D).

Use `limits[redis]`, not `limits[async-redis]`: slowapi calls the **sync**
`limits` API (`storage_from_string` + `limits.strategies.STRATEGIES`), so
`coredis` would be installed and never used. Note the consequence — the sync
client is called from async request handlers, so each rate-limited request
does a blocking Redis round-trip on the event loop.

`app/core/public_access_lockout.py` reads the **same**
`RATE_LIMIT_STORAGE_URI`, so configuring Redis fixes both limiters at once.
That module deliberately **fails open** on storage errors (round 8-9C): a
Redis outage silently disables the phone-lockout counter rather than taking
the public inspection flow down. Monitor Redis accordingly.

## 7. Security Headers

```python
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
from starlette.responses import Response


class SecurityHeadersMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next) -> Response:
        response = await call_next(request)
        response.headers["X-Content-Type-Options"] = "nosniff"
        response.headers["X-Frame-Options"] = "DENY"
        response.headers["Strict-Transport-Security"] = (
            "max-age=31536000; includeSubDomains"
        )
        response.headers["Referrer-Policy"] = "strict-origin-when-cross-origin"
        response.headers["Permissions-Policy"] = (
            "camera=(), microphone=(), geolocation=()"
        )
        response.headers["Content-Security-Policy"] = (
            "default-src 'self'; "
            "script-src 'self'; "
            "style-src 'self' 'unsafe-inline'; "
            "img-src 'self' data: https:; "
            "connect-src 'self' https://login.microsoftonline.com; "
            "frame-ancestors 'none';"
        )
        return response


app.add_middleware(SecurityHeadersMiddleware)
```

## 9. PII Handling

### 9.1 What Counts as PII

- Email addresses (when paired with name/identifier)
- Phone numbers
- National ID, passport
- Address (street level)
- Date of birth
- Financial info (account, card numbers)
- Health information

### 9.2 Rules

| Action | Rule |
|---|---|
| Logs | Mask/truncate PII (`first 3 chars + ***`) |
| Errors | Never include PII in error messages |
| Analytics | Hash identifiers before sending to third parties |
| Backups | Encrypt at rest (Postgres has `pgcrypto`, disk-level encryption) |
| Export to CSV | Require explicit user action + audit log |
| Sharing with AI | Mask before sending to Claude API (or use anonymization) |

### 9.3 Masking Utility

> Implementation อยู่ใน [`logging.md`](logging.md) §4 — single source of truth
>
> Helpers: `mask_email()`, `mask_phone()`, `mask_pii_in_text()` ใน `app/core/pii.py`
> Phase 1.5: `LoggerWrapper` ใช้ `mask_pii_in_text()` เป็น default — AI ไม่ต้อง remember

### 9.4 PII in Logs

```python
logger.info(
    "user_login",
    user_id=str(user.id),         # ✅ UUID is opaque
    email=mask_email(user.email), # ✅ masked
    auth_provider=user.auth_provider,
)
# ❌ Never:
# logger.info("user_login", email=user.email, password=payload.password)
```

## 10. Audit Logging

> **v3.0:** `audit_logs` ถูก merge เข้า `activity_logs` (logging.md §1) — แยกด้วย `is_security_event=True` + `risk_level` flag
>
> Implementation, schema, service → [`logging.md`](logging.md) §1
>
> Single `ActivityLogger` ทำหน้าที่ทั้ง audit + user activity — ลด duplicate code paths

### What to Audit (still applies — wire via `ActivityLogger`)

**Required (`is_security_event=True`, risk_level=high):**
- Auth events: login, logout, failed login, password change, 2FA setup, invite accept → `log_login()`
- Permission/role changes → `log_permission_change()`
- Admin actions: user create/delete, BU access change → `log(action_type="update", risk_level="high")`

**Required (`is_mutation=True` or `is_sensitive_read=True`):**
- All mutations on business data (create/update/delete) — via `@audited` decorator
- Data export / view PII / view other users → `log_export()` / `log_sensitive_read()`
- Permission failures (403 responses) → `log(action_type="permission_denied", risk_level="medium")`
- High-risk operations (AGENTS.md §4)

**Not required:**
- Regular read operations (GET) — unless on PII-heavy resources
- Routine system jobs (unless they fail) → use `SystemLogger` แทน

## 11. Dependency Scanning

### 11.1 Backend (Python)

```yaml
# .github/workflows/security.yml
- name: pip-audit
  run: |
    pip install pip-audit
    pip-audit -r requirements.txt --strict
```

### 11.2 Lock strategy ก่อน go-live (mandatory)

`pyproject.toml` ของ scaffolded backend ใช้ **lower-bound floors** (`>=X.Y.Z`)
ซึ่งสะดวกตอน dev แต่จะปล่อยให้ production pull version ที่ **ใหม่กว่าที่เคยทดสอบ** —
หรือถ้า floor ตกหลัง CVE จะติด vulnerable version โดยไม่รู้ตัว

ทุก project ที่จะขึ้น production ต้อง:

1. **Pin ลง requirements.txt** ก่อน build production image:
   ```bash
   cd backend
   pip install -e .[dev]
   pip freeze > requirements.lock.txt
   ```
   Commit `requirements.lock.txt` เข้า git — Dockerfile ใช้ไฟล์นี้แทน `pyproject.toml`
   ตอน `pip install -r requirements.lock.txt`

2. **Re-audit หลัง pin**:
   ```bash
   pip-audit -r requirements.lock.txt --strict
   ```
   ถ้าเจอ vulnerability → bump floor ใน `pyproject.toml`, re-pin, re-audit

3. **CI runs both**:
   - `pip-audit` ของ `pyproject.toml` (catch floors ที่ตก behind CVE)
   - `pip-audit` ของ `requirements.lock.txt` (catch ของจริงที่จะ deploy)

4. **Bump cadence**: pin ใหม่ทุก sprint หรือเมื่อ Dependabot/Renovate เสนอ security patch
   หากใช้ `[tool.uv]` หรือ `[tool.poetry]` แทน, ใช้ native lock file (`uv.lock`, `poetry.lock`)
   เป็น source of truth ก็ได้

## 12. Incident Response Checklist

### 12.1 When a security incident is suspected

**Step 1: Triage (within 1 hour)**
- [ ] Identify the type: data leak, unauthorized access, malicious code, DoS
- [ ] Estimate scope: how many users/records affected?
- [ ] Determine if attack is ongoing or contained

**Step 2: Contain (within 4 hours)**
- [ ] Block compromised credentials/tokens (rotate JWT_SECRET_KEY = all sessions revoked)
- [ ] Disable affected user accounts (`is_active = false`)
- [ ] Block attacker IP at WAF/firewall if known
- [ ] Take affected service offline if needed
- [ ] Preserve logs, do not delete (forensics)

**Step 3: Eradicate (within 24 hours)**
- [ ] Identify root cause via logs + audit table
- [ ] Patch vulnerability (code fix, dependency update, config change)
- [ ] Verify fix in staging before production deploy

**Step 4: Recover**
- [ ] Restore service
- [ ] Reset affected user passwords; require re-login
- [ ] Monitor logs for anomalies for 7+ days

**Step 5: Postmortem (within 1 week)**
- [ ] Document timeline, impact, root cause, fixes
- [ ] Notify affected users per legal requirements (PDPA — within 72 hours for Thailand)
- [ ] Update runbook with lessons learned
- [ ] Add detection/prevention to prevent recurrence

### 12.2 Communication Plan

| Audience | When |
|---|---|
| Engineering team | Immediately upon suspicion |
| Security/Privacy officer | Within 1 hour (if data is involved) |
| Management | Within 4 hours |
| Affected users | Within 72 hours (PDPA Thailand) |
| Regulator (PDPC Thailand) | Within 72 hours (if breach affects 1000+ people or sensitive data) |
